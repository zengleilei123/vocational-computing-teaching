# 四项先修诊断：我现在能独立做到哪一步？

先完成 [首次启动](START.md)。四题建议用 20–25 分钟，目的是找到下一步需要的支持。首次尝试请自己预测、运行和解释；可以查项目文档，不请 AI 直接代答。之后可以使用提示或请同伴讲解，但要标出哪些部分得到帮助。

每题交付真实观察，不用把“不知道”写成“已经掌握”。题目只使用学生包中的材料和自己新建的小练习，不修改原评测器。

## D1：读函数、循环和条件，再做一个小修改

**输入。**在自己的练习目录新建 `diagnostic_count.py`，输入下面的小程序：

```python
def count_target(rows):
    total = 0
    for row in rows:
        for cell in row:
            if cell == '#':
                total += 1
    return total


rows = ['S#.', '..#', '..G']
print({'rows': len(rows), 'target': count_target(rows)})
```

**操作。**先写下你预测的输出，再运行：

```bash
python diagnostic_count.py
```

把条件中的 `'#'` 改为 `'.'`，再次先预测后运行。保持输入地图不变。

**交付。**两次预测、两次实际输出、改动的一行，以及一句说明：`total` 为什么要在循环开始前设为 0？函数返回的值和最后打印的字典有什么关系？

**自己检查。**你能指出列表、字符串、循环、条件和返回值，并用逐格计数核对结果。只复制输出而无法解释计数过程，还需要补练。

**渐进提示。**先在纸上逐行圈出目标字符；仍不清楚时，画一张“当前格子／是否满足条件／累计值”小表；最后再请同伴陪你跟踪其中一行，剩余两行自己完成。

**就地补练。**另写一张合法三行地图，保留唯一 S/G，在纸上数好目标字符再运行。让同伴只改变其中一个格子，你独立预测输出怎样变化。补练通过后，进入工作簿的阶段 1。

## D2：区分页面、服务端和 JSON

**输入。**启动原机器人服务，保持第一张预设地图。打开浏览器开发者工具的 Network（网络）面板，点击一次 BFS，找到 `/api/solve` 请求。

逐处打开这些真实文件核对：

- [static/index.html](../../../projects/robot_playground/static/index.html)
- [static/app.js](../../../projects/robot_playground/static/app.js)
- [server.py](../../../projects/robot_playground/server.py)
- [engine.py](../../../projects/robot_playground/engine.py)

**操作。**记录请求的方法、路径、状态码、一项请求字段和一项响应字段。然后用箭头串起“点击哪个控件 → 哪个前端函数 → 哪个服务端路由 → 哪个业务函数 → 页面哪里显示结果”，每个环节在源码中核实。

**交付。**一条调用链、至少三个核对过的文件位置，以及下面四项的分类：

| 对象 | 在哪里运行或存放？ | 你依据的观察 |
|---|---|---|
| 页面控件和前端脚本 | 待填写 | 待填写 |
| Python 请求处理代码 | 待填写 | 待填写 |
| 请求中的 `grid` JSON 数据 | 待填写 | 待填写 |
| 当前起点是否已经把地图存进数据库 | 待核实 | 待填写源码或运行依据 |

**自己检查。**你能说明一次请求的输入输出，以及“JSON 数据”和“执行它的代码”为什么需要区分。不能只给出一条没有文件证据的箭头链。

**渐进提示。**先在网络面板筛选 `solve`；再在前端文件中搜索 `/api/solve`；最后在 Python 文件中搜索相同路径，核对其调用的函数。

**就地补练。**重新点击 Dijkstra，仅比较这一请求与 BFS 请求的字段变化，不改代码。随后关掉前面的笔记，自己重新找到一次响应及其页面结果。完成后再做阶段 2 的状态与存储设计。

## D3：从报错找到真实文件和行号

**输入。**保留已经能运行的 `diagnostic_count.py`。在自己这个小文件末尾单独加一行：

```python
print(diagnostic_marker)
```

**操作。**再次运行小程序，完整读一遍报错。记录报错中的文件、行号、异常名称和最后一行说明。提出一个原因假设，只恢复刚才这处练习改动，再重跑确认。

**交付。**失败时的命令和原始输出、指出的文件与行号、原因假设、恢复后的实际输出。解释：为什么重新启动机器人服务不能修复这个小文件的问题？

**自己检查。**你能在编辑器打开报错指向的位置，说明这行与错误之间的关系，并用重跑证明恢复。不要把“有红字”当成已经定位根因。

**渐进提示。**先读 traceback 最后一行，再向上找自己的文件路径；与刚才只改过的一行对照；如果仍无法定位，请同伴指出报错中哪个部分是文件位置，其余由你完成。

**就地补练。**让同伴在这个小练习的副本中把一个变量名拼错，保留原正确副本。你不看其改动记录，先根据真实报错定位，再比较两个文件。练习结束保留证据并恢复小文件，不向项目源码注入故障。

## D4：通过、失败和没有运行不是一回事

**输入。**下面是供辨认的示例片段，**不是你的运行证据**：

```text
片段甲：Ran 37 tests ... OK
片段乙：Ran 1 test ... FAILED (failures=1)
片段丙：Ran 0 tests ... OK
```

**操作。**说明三种结果分别能支持什么结论，再从工作根目录真正运行：

```bash
python -m unittest discover -s projects/robot_playground -p "test_*.py" -v
```

**交付。**你实际运行的命令、实际测试数量、最后结果、一个测试名和输出位置。原起点应发现 37 项；如果不同，记录实际数量并核对目录与筛选参数，不能修改输出凑数。

**自己检查。**能回答：只有旧项目测试通过，是否证明自己尚未实现的存档功能已经可用？如果本机 HTTP 被环境限制而未能运行，应怎样记录？

**渐进提示。**先分别圈出每段中的“数量”和“结果”；再查看本次命令到底扫描哪个目录；最后选择一个真实测试名，说出它观察的行为。

**就地补练。**在正确根目录重新执行同一命令，自己找到第一条测试名和最终汇总。将“已执行且满足预期”“已执行但不满足”“尚未执行”“被缺依赖或环境条件阻塞”分别对应到 [提交模板](SUBMISSION.md) 的四种状态。
