# 项目三：实训验收证据接回智能助教（学生任务书）

## 业务委托

教师分别验收设备预约与报修分类项目，按能力项记录分数。系统应读取已复核的成绩证据，更新练习记录，再给出学习建议；重复上传不能增加练习次数，错误批次不能部分入库，模型不能自行更改成绩或批准计划。
建议4学时；先修：前两个项目、CSV、SQL事务及CoursePilot先修图。

## 数据合同

CSV头部固定为`evidence_id,student,project,topic,score`。
`evidence_id`对应一次明确的项目能力项验收；`project`只能为booking/tickets；topic须属于项目映射和CoursePilot课程表；score为0—100的有限数。
示例[data/assessments.csv](../data/assessments.csv)为5条合成的教师评分，不是测试通过数量换算的分数。

相同证据、相同内容再次导入：跳过，不重复写入。
相同证据、不同分数：拒绝；正式改分需要单独、可审计的更正流程，本课未实现。
同一批次出现一条无效或冲突证据：全部拒绝，不留下已处理前缀。

## 课堂任务

第1—2学时：先画数据流，编写全批校验，再用事务写入原有Store的attempts与metadata证据登记。对比“按行立即commit”会产生的半批入库错误。
第3—4学时：调用原有progress和draft，检查学情统计和补学路径；分析为什么平均分不能直接等同真实能力，为什么计划仍需人工确认。

## 一个完整验收例子

首次导入5条，重放导入0条、跳过5条。
合成学习者Python平均87.5、算法80、SQL45。CoursePilot现有演示阈值70下，目标agents的补学顺序为`sql → api → agents`，计划状态是`pending`。
这里使用既有规则，不声称这是经过教育研究验证的掌握度模型。未测能力不等于完全不会，只表示当前无足够证据。

## 分层任务

基础：字段校验、未知topic/越界分数拒绝、学情查询。
提高：相同证据幂等、同ID改分拒绝、全批回滚。
挑战：设计多次评分、重修、教师复核的审计方案；比较均值、最近一次、加权均值对建议的影响，并解释各自偏差。不要直接修改既有算法使示例输出“更好看”。

## 验收与评分

业务正确性35；事务与重放测试30；数据流解释20；隐私与人工确认边界15。
必须演示：未确认不导入；同批出现nan全部拒绝；新记录在前、冲突记录在后仍全部回滚；同一CSV重放不改变attempts计数；学习计划不自动批准。
个人答辩：evidence_id为什么不能用每次上传时随机生成的ID？数据已写入与教学效果变好是否是一回事？

## 运行与边界

`python -m projects.classroom_practice.app feedback`
参考解：[assessment.py](../assessment.py)。它直接使用[原有Store](../../coursepilot/core.py)，而非另造一个不相连的学习系统。
`confirmed=True`只是本地操作的显式确认，不等于完成教师身份认证。当前没有正式教务写入、自动批改学生代码、真实学生数据或HTTP/LLM工具接入。课程需同时讲明这些未实现部分。
